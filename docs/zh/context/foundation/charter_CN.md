# Tools Registry — 章程（charter）

## 2026-08 的变化 — 目录（catalog）成为前门

下面的章程描述的是一个**保险库（vault）**：你团队自己的密钥与技能，无需把凭据到处传递就能被调用。这部分已经发布，而且至今仍与文档所述完全一致。但它回答的是"共享我们已经拥有的东西"，而产品现在的重心是另一个问题：**"获取你尚未拥有的东西。"**

treg 维护着一个经过策展（curated）的端点（endpoint）目录，覆盖多家供应商（SEO、反向链接、社媒、数据增广、广告、抓取），并以**自有密钥**提供其中符合条件者，按调用次数从预收余额中计量计费。其卖点是 *"OpenRouter，但面向智能体工具而非模型"* 以及 *"为任务而请求，而非为工具"* —— 因为智能体所需的工具，往往藏在没人会为一次运行去订阅的付费墙之后。

这对任何阅读本片段的人意味着：

| | |
|---|---|
| 两个半边 | **目录（catalog）**（公开、计量）与**你自己的工具**（你的、永不计量） |
| 哪个优先 | 你自己的凭据永远胜过 treg 的，自动生效 |
| 我们使用的词 | `tool` · `the catalog` · `your own tools`。**不要**对任一半边使用"vault""marketplace"或"registry"——`registry` 现在仅指服务端/部署 |
| 尚未构建 | 同一能力**不同供应商之间**的自动路由或故障转移。`treg catalog search` 会比较它们；**选择由调用者决定**。treg *可以* 做的（当某个部署开启它时，见 [capacity](../ops/capacity.md)）：如果它面向某供应商的**自有**账户耗尽，则通过转发（relay）提供**同一端点**——同样的请求、同样的响应形态、转发方的真实价格，并经 `X-Treg-Served-Via` 披露；团队可以选择退出。**第一方路由端点**（`treg.<capability>`，由已验证的适配器生成）是显式的 opt-in，调用者请 treg 在供应商中做选择；每个端点总会指明实际提供服务的子节点（child）并返回其原始响应体（见 [catalog](../architecture/catalog.md) § Routing） |

记账与计量：见 [money](../architecture/money.md)。端点数据及其定价规则：见 [catalog](../architecture/catalog.md)。

> **状态：** 已发布并在 `treg.to` 上运行（Render，多租户；`treg.superdesign.dev` 为旧版别名）。本片段记录了 2026-06-30 启动会的**原始愿景**以及代理背后的"为什么"；已发布的细节存在于 architecture/interface 各片段中。
>
> **⚠ 请先读下一节。** 产品的重心在 2026 年 8 月发生了转移。本行以下的内容依然为真、依然在运行——但它已不再是产品的全貌，也不再是 treg 对外呈现的方式。

一个远程的**注册表，把团队的技能变成可共享、可调用的工具。** 任何团队成员的**智能体**（Claude Code / Codex / Gemini）——或人通过 CLI/API——都可以调用一个工具，**而无需拥有它的凭据或重新构建它**。（在内部我们把它看作一个 *skill 注册表*：技能 + 数据动作；"tool registry" 是工作代号。）

> **承重理念 — 代理（proxy）。** 消费者发起**真实的向上游 API 调用**（它已经懂这个 API，例如 PostHog）并带上自己的参数；该调用被**路由经过我们的代理域名**，由代理**在服务端注入鉴权**。消费者永远不持有密钥。这就是全部要点——而且它能扛住上游 API 的版本变化，因为我们不建模 API，我们只做转发（relay）。

## 为什么（Why）
- **易于共享 / 上手** — 给队友*一个端点*覆盖一切；新增一个系统无需给每个人重新接线。例如：一位新来的市场经理调用 PostHog 工具时**无需 API key**。
- **消费者往往是智能体，而非人。** 从团队起步；之后任何人使用 Claude Code/Codex 等皆可。
- 之后：**权限等级 + 审计日志**（谁用了什么）。

## 什么是"工具"（tool）
一个**技能 + 它的鉴权**。需要支持的鉴权形态（来自真实的 `superdesign-agi/.claude/skills/`）：纯**环境变量（ENV vars）**、**`.secret/` OAuth 令牌文件**（如 GCP、Google Ads）、**CLI 鉴权**服务，以及完整的 **OAuth** 连接流——而不仅仅是 API key。MCP 是**可选的，后续再说**。

## 形态（MVP）
- **API + CLI + 一个注册表 skill。** 这一个 `tools-registry` skill 既是消费者*调用*工具的方式，也是创建者/管理员*创建 / 推送 / 列出 / 更新 / 删除*工具的方式（完整的 **CRUD**，通过 API 与 CLI 均可）。
- **上手流程：** 一个智能体读安装文档 → 安装 CLI → 用户鉴权 → 智能体识别本地的技能 + 环境变量/密钥，**上传/注册**它们 → 返回一个端点 + 给团队的分享说明。（Web 仪表盘 = 第二阶段；最小化，GitHub/Vercel-secrets 风格。）
- **从第一天起就有鉴权**（用于存储每用户/每组织的密钥）。目前**允许所有人**注册；授权分级后续再做。

## 安全（MVP vs 后续）
- **MVP：** 依赖 **TLS/HTTPS**（如同把密钥粘贴进 GitHub/Vercel）。代理已经实现了"在本地无密钥的情况下使用一个工具"（密钥存在于注册表中；成员可以针对别人上传的密钥构建/注册工具——一个占位方案）。
- **后续（极致）：** 运营方注册会**生成一枚本地私钥**并签署凭据，使得只有服务端能解密它们（银行级）——可防拦截。非 MVP。

## 部署与扩展
先在测试服务器上 → **Render**（更易调试）。代理很**薄**（IO 密集型，低 CPU/内存）→ 扩展便宜；每租户廉价机器 vs 共享 = **未定**，构建得很薄，所以两种方式都行。

## 边界 / 关系
- **目前独立**，与 SuperDesign 分离。可能**之后与 Loopni 合并**（loops + 上下文 + 工具访问合一）；Loopni 本身可能成为注册表中的一个工具/运行时。
- **区别于 Intel Factory**（`intel-factory/`，它为每个业务构建知识*湖*）。这里共享的是*工具*，不是知识。大概率会有一个类似 Intel-Factory 的**社区 PR-back** 流程用于新增连接器。

## 首个试验场
把 `superdesign-agi/.claude/skills/` 中的**每一个技能**自动转换为一个工具并逐一测试（PostHog、GSC……）——证明*制造任意工具的机器*，覆盖每一种鉴权形态。之后的新工具 = 人工添加。
