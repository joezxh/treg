# Recipes —— 那些决策

一个 **recipe（配方）** 是一个由工具组成的工具。它调用工具一，调用工具二，合并两个答案，在合并结果上调用工具三，然后发一封邮件。treg 在调用方的账号下，为调用方跑完整个流水线。

这个文件是 2026-09-07 与 owner 的一次问答记录，在任何设计工作之前。**问题逐字保留。** 每个问题下面是 owner 批准的回答。owner 在问题没问到的地方补充了东西的，写在"owner 补充"下。

目的：下面没有任何设计决策建立在猜测上。

---

## owner 设定的框架

- 团队先写很多 recipe。然后邀请外部的人提交他们自己的。
- 贡献路径是一个 pull request：创建、提交、检查、验证、批准、加入目录。
- 目录页展示每个 recipe 及其状态：treg 构建的、已验证的、已提交但还没验证的。
- 脚本语言是 JavaScript。一种大家都懂的语言。解释还是编译是实现选择。
- 有些 recipe 只有步骤、不需要脚本。那些不需要沙箱。
- treg 自己的沙箱跑 treg 构建或验证过的 recipe。一个团队想要自己的沙箱是以后、付费的事。
- 脚本永远不持有密钥。它点名一个工具并给出输入；treg 注入凭据。
- 每个计量的步骤都从调用方余额扣减，完全像今天的直接调用。recipe 本身不收额外费用。
- 第一版在请求内从头跑到尾。
- 这个产品在内部叫 tool hub。这一类的一个东西就是一个 recipe。

## 第一轮 —— 契约的形态

**1. 一个 recipe 在运行前，是否在它的 manifest 里声明它可能调用的工具？那份清单就是审阅者读的、也是阻止脚本够到任何其他东西的东西。**
是，必填。

**2. 当一个 recipe 需要一个调用方没有的密钥时会发生什么？**
在任何步骤运行前拒绝，并确切点名要去连什么，这样一次无法完成的运行不会扣任何费。

owner 补充：调用方读消息、加上密钥、然后继续。当工具不需要调用方的任何密钥时，调用用 treg 的密钥服务，并从调用方余额扣除。

**3. 一个 recipe 是否像目录端点声明其参数那样，声明它的输入和输出字段？**
是。那正是让它带着价格进入搜索、并让一个 agent 无需读代码就能调用它的东西。

---

## 第二轮 —— 它如何到达调用方

**1. 一个 agent 如何调用一个 recipe？**
treg 今天只有一条调用路。一个 recipe 可以带着自己的 id 走这条路，或者另开一条自己的路。
同一条路，`/call/<recipe id>`。那样 CLI、MCP 工具和每个插件在第一天无需改动就服务 recipe。

**2. 一个 recipe 是否出现在与端点相同的搜索里？**
一个 agent 按它想要的工作搜索。一个 recipe 是由若干端点组成的更大的工作。
是，同一个搜索，带一个标记说明它是 recipe 以及它做几步。

**3. 运行前我们展示什么价格？**
单个端点有一个价格。一个 recipe 的价格取决于它的输入，因为一个步骤可能遍历行。
展示默认输入下一次运行的价格，并让调用方为整个运行设一个上限。当下一步会越过上限时运行停止。

**4. 一个 recipe 可以调用另一个 recipe 吗？**
它有用，但它也会制造循环和一笔谁都读不懂的成本。
第一版不行。一个 recipe 只调用工具，一层深。

**5. 一个 recipe 返回什么？**
它可以原样返回最后一步的答案，或者它声明的一个对象。
recipe 声明的一个 JSON 对象，这样 agent 在调用前就知道字段名。

**6. 六步里的第四步失败。调用方拿到什么？**
要么一个错误，要么已完成的那部分带一个警告。
一个错误，说明哪一步失败、跑了什么、扣了什么。一个 recipe 可以把某一步标为允许失败，然后运行继续。

**7. 一次运行可以多久，可以多少步？**
运行坐在一个 HTTP 请求里，所以调用方在等。
第一版 120 秒、20 步，两者都按 recipe 声明在那些上限下。

**8. 一个 recipe 的源码在哪？**
贡献路径是一个 pull request，所以源码大概像目录一样是仓库里的文件。另一个选择是数据库里的一行，在控制台编辑。
仓库里的文件，每个 recipe 一个文件夹，完全像目录。一个控制台编辑器以后可以来，用于团队自己的私有 recipe。

**9. 一个发邮件的 recipe 和一个只读的是否标记不同？**
一次读可以安全重试。一次发送不行。
是。一个 recipe 声明它写，目录展示它，而写的那类像 Claude connector 面已经把读调用和写调用分开那样被分开。

## 第三轮 —— 一个 recipe 的生命

**1. 当一个 recipe 在人们用了之后改了，会发生什么？**
作者修一个 bug 或改一个字段名。一个调用方可能依赖旧形态。
每个 recipe 带一个版本号。目录服务最新的。一个调用方可以通过在 id 里点名版本来要一个旧的。

**2. 一个文件还是两个？**
一个没逻辑的 recipe 只需要一份它的步骤描述。一个有逻辑的 recipe 还需要一个脚本。
永远一个 manifest 文件。旁边的脚本文件，只在需要时。没脚本意味着 manifest 里的步骤按顺序跑。

**3. 我们如何在合并前知道一个提交的 recipe 能工作？**
一个审阅者没法靠读来判断一个流水线。
每个 recipe 随附一个 check 文件：样本输入和它至少要返回的东西。审阅跑它一次，真实地，结果进 pull request。

**4. 一个 recipe 是否有一个健康状态，像端点的可靠性那样？**
recipe 用到的端点可能坏，然后 recipe 就坏。
是。check 文件的一次定时运行，目录展示状态。一个失败的 recipe 在搜索里下沉并说明为什么。

**5. 脚本在哪跑？**
在 Web 服务器自己的进程里，还是在一个独立的短生命进程里。
一个独立的进程，没有自己的网络、有内存上限和时间上限。一个坏脚本于是碰不到服务器或另一次运行。

owner 补充：脚本完全没有网络。每次工具调用都走脚本被给的 treg context 对象出去。没有别的路到网络。

**6. 脚本可以看什么？**
它可以只看自己的输入，或者也看团队名、余额、token。
只看自己的输入和它跑过的步骤的答案。与团队无关的东西、没有余额、没有 token、没有环境。

**7. 调用方对运行能看到什么？**
一个流水线在只返回最终答案时是 opaque 的。
一个有序的步骤列表，带每个的工具、状态、时间和成本，外加 recipe 自己的日志行。步骤 body 保持在外，除非 recipe 返回它们。

owner 补充：这个可见性很重要。一个看着的人看到工具的级联并知道它在跑。一个 API 调用方作为数据看到同样的。

**8. 一个发邮件的 recipe，在超时后重试。它会发两次吗？**
treg 已经有单个调用的重试标签。
同一个标签覆盖整个运行。一次带同标签的重试用存储的结果返回并什么都不再跑。

**9. 一个团队可以同时跑几个 recipe？**
每次运行持有一个请求和一个沙箱长达两分钟。
每团队同时四个，之上明确拒绝，说明何时再试。

## 第四轮 —— 数据、身份与所有权

**1. 在一个没脚本的 recipe 里，第二步如何用第一步的答案？**
步骤必须传数据。一套完整的表达式语言是要学的另一件事、也是要审阅的另一件事。
只两样东西。一个读取更早一步某个字段的占位符，以及一个对列表的重复。再多就需要脚本。

owner 补充，而且这塑造了设计：一个步骤点名一个更早的步骤和它的一个字段，含嵌套字段，写成 `$0.field.subfield`。那些引用构成依赖图。一个不点名任何人的步骤没有依赖，立刻开始。treg 把每个就绪的步骤一起跑，然后是下一组就绪的，直到结束。没有手写声明。例子：四步，其中三步需要二、二步需要一、四步不需要任何人。那么四和一起开始，二跟一，三跟二。另一个例子：三分别需要一和二，四不需要任何人。那么一、二、四一起开始，三在一和二都完成后跟。算法必须保持简单可读。

**2. 当一个 recipe 点名一个工具，它点的是目录 id 还是团队自己的工具名？**
一个团队自己命名自己的工具。一个团队把它的 Stripe 工具叫"stripe"，另一个叫"billing"。一个共享 recipe 不可能知道那个。
只用目录 id。treg 的阶梯于是用团队自己的该供应商密钥（当他们有时），没有时用 treg 的密钥。

**3. 每次运行是否得到一个 id 和一个展示级联的页面？**
你想要调用方看着流水线进行。
是。回复带一个 run id 和步骤列表。那个 id 上的一个页面展示同样的级联，控制台读它。

**4. 运行结束后我们保留它吗，保留多久？**
今天每一步都已经写进调用日志。运行级是新的。
每次运行一行带它的步骤，保留 30 天。调用方看自己的运行。管理员看团队的。

**5. 每一步都过调用方自己的规则吗？**
一个团队封锁一个主机。一个成员被限制在三个工具内。
是。每一步过和直接调用同样的门。一个被封锁的步骤停止运行并点名拦住它的规则。

**6. 一个 recipe 可以向调用方要一个 treg 不存的秘密吗？**
有些站点需要那个人自己的 cookie，不是 API key。那就是我们在 Crawl4AI 撞到的。
可以，一个标记为 secret 的输入。永不记录、永不存储、永不进 trace，且运行永不缓存。

**7. recipe 发了邮件，然后第五步失败。我们撤销邮件吗？**
一封邮件收不回。
不撤销。trace 说清做了什么。给作者的规则：把写放在最后。

**8. 一个没脚本的 recipe 不需要沙箱。一个团队可以从第一天起保留一个私有的吗？**
沙箱是等付费方案的那部分。
可以。一个团队今天就可以注册一个只有步骤的私有 recipe。一个带脚本的私有 recipe 等团队沙箱。

**9. 一个 recipe id 长什么样，名字归谁？**
目录用由供应商和一项工作组成的点号 id。recipe 来自很多作者。
作者的 handle 加 recipe 名，作为一个 id。treg 自己的 recipe 用 treg 的 handle。一个名字属于其作者，不能被夺走。

**10. 一个作者可以在 pull request 之前从自己的文件夹跑一个 recipe 吗？**
等审阅来发现一个拼写错误太慢。
可以。一条命令用作者自己的 token 从文件夹跑 recipe。每一步都去真实 treg 并照常计费。

## 第五轮 —— runner 的规则

**1. 步骤之间按编号还是按名字互相引用？**
`$0.data.email` 很短。但如果你在中间插一步，后面每个编号都移了。
每步得到一个短名字，引用读那个名字，像 `$lead.data.email`。编号仍作为已那样写的那些的别名有效。

**2. 一次运行里可以同时跑几步？**
四个独立步骤可能都立刻开始。每一个持一个连接和钱。
同时四个。运行的钱上限和时间上限在那之上仍适用。

**3. 一个步骤遍历 500 行列表。什么拦它？**
那是一次 recipe 运行发出 500 个调用。
每项为一步计。所以步数和钱上限都计它们，而 recipe 声明自己更小的限制。

**4. 两步一起跑。一个失败。另一个怎样？**
它已经发出、已经付费。
让它跑完，别起新的，返回带完整 trace 的错误。trace 展示完成的和失败的那一个。

**5. 没脚本的路上有条件吗？**
"只在第二步找到东西时才跑第三步"是常见情况。一套完整条件语言是一门语言。
只有一条规则。一个步骤可以说"当我读的值是空时跳过我"。trace 标它跳过。要多就需要脚本。

**6. 有只改数据、不调工具的步骤吗？**
你的第一个例子在下一次调用前合并了两个答案。
没脚本的路上没有这种步骤。一个读两个更早步骤的步骤已经同时收到两者，那正是合并。真正的逻辑进脚本。

**7. 调用方在运行进行时看到进度，还是只看最终答案？**
控制台可以轮询运行页。一个 API 调用方持一个请求开着。
第一版在最后返回整个 trace，运行页在跑的时候轮询。API 上的实时流是以后加的。

**8. recipe 声明的输出如何被填？**
recipe 承诺字段名。得有东西填它们。
输出块把每个字段映射到一个引用，语法同步骤。一个脚本 recipe 返回对象本身。

**9. treg 重试一个失败的步骤吗？**
treg 今天按设计不重试单个调用。
第一版不重试。运行停止，trace 说哪一步失败、为什么。

**10. 一个步骤返回零行。那是失败吗？**
没结果对一次搜索是正常答案。
不是。零行是数据，不是失败。只有被拒绝或失败的调用停止运行，而"空时跳过"规则处理其余。

## 积压项，按被提到的顺序

1. **一个作业队列。** 第一版在请求内跑。一个队列和一个 worker 以后来，然后一个 recipe 可以跑远超过 120 秒。
2. **一个调用 recipe 的 recipe。** 带循环控制，这样不能成环、成本保持可读。
3. **失败步骤的重试。**
4. **API 上的实时进度**，不只是运行页。
5. **团队自己的沙箱。** 一个付费方案，也是通往带脚本的私有 recipe 的门。
