# 客户级计费 —— 构建者把 treg 转售给自己的客户

**状态：**已规划，待审阅。尚未构建。写法是留给一个不了解背景的维护者直接接手；不假设来自设计讨论的任何上下文。

## 谁在提需求，要什么

构建者正把 treg 集成进他们自己的 agent 产品。他们的最终客户使用该产品；该产品在底层调用 treg。构建者需要知道并限制他们**每个**客户消费了多少，并向那些客户自己计费。

## 一切所遵循的边界决策

**treg 计量并执行；构建者变现。** treg 永远不向构建者的终端客户计费，永远不持有他们的卡，永远不设定他们的价格。treg 欠构建者的恰好三件事：

1. **归因** —— 客户 X 本月消费了什么
2. **执行** —— 在构建者设定的上限处拒绝客户 X
3. **导出** —— 干净到足以据此开票的数字

下面所有内容都是这三件事，没有别的。毛利、对终端客户的价格，以及开票是构建者自己的 Stripe 和他们自己的事。

## 两种模型，一种已上线

| 模型 | 谁付 treg | 状态 |
|---|---|---|
| **客户付费** | 每个终端客户，他们自己的团队 + 余额 | **已上线。** 构建者的产品通过 treg 的 OAuth 服务器（同意页、团队选择器）连接。为 ChatGPT 而建，刻意做到客户端无关 |
| **构建者付费** | 构建者，一个组织，一个余额 | **本计划** |

客户付费适合那些用户本来就会想要自己 treg 的开发者工具产品。构建者付费是大多数构建者所指的意思，也是缺口所在。

## 构建者付费：设计

### 元数据袋，以及保留的 `customer` 键

刻意只用一个机制 —— 而不是每个特殊概念一个专用头。每次调用可携带一个小标签袋，`customer` 是其中的一个保留键：

    POST /call/hunter.people.email.find
    X-Treg-Token: <builder org token>
    X-Treg-Meta: customer=cust_8123, feature=email-finder, env=prod

在 MCP 上，同一回事是 `call` 工具上一个可选的 `meta` 字典参数。

权力划分：

- **任何键**都被记录，并可在用量报告里分组（`group_by=feature` 与 `group_by=customer` 工作方式相同）。这是 AWS 成本分配标签模型；Anthropic 的 API 也这么做（免费元数据，一个受宠的 `user_id`）。
- **只有 `customer`** 携带强制执行：预算、`blocked`、幂等性作用域，以及每客户 token 的升级路径。这不能泛化的两个原因是：针对任意标签组合的预算检查会在热路径上变成 N 次查找而不是一次，而重试作用域恰好需要**一个**分区维度（一个标了 `customer=a, feature=b` 的调用，对"哪一个来分区它的幂等键"没有正确答案）。

未来的特殊键通过在该袋里保留另一个键来获得语义，绝不是通过加一个头。

袋规则：每次调用最多 5 个键；键和值是透明字符串，最多 32/128 字符，按原样存储。文档必须说"用你内部的 id，而不是邮箱" —— 标签会落进审计行和用量导出，所以 PII 不属于它们。没有袋意味着与今天的行为完全一致。

伪造从构造上就不是问题：唯一可能误标的是一个构建者，而一个标签所触碰的预算和报告也只是构建者自己的。

### 第 1 块 —— 记录袋（归因）

审计行已经带一个 `telemetry` 字典，账本结算已经带一个 `meta` 字典。袋里的键合并进各自。无 schema 变更；归因变成一次查询。

### 第 2 块 —— `CustomerBudget`（执行）

新表，以组织为作用域（进入 `ORG_SCOPED_MODELS`（`domain/governance/teams.py`）- 如果忘了，删除级联测试会抓住它，以前抓到过）：

    CustomerBudget: org_id, customer (string), monthly_cap_micro | daily_cap_micro (nullable),
                    calls_per_day (nullable), status (active|blocked), created/updated

CRUD 在 `/orgs/{id}/customers` 下。执行位于和 `/call/` 路径里 `_enforce_daily_cap` 相同的插入点，并以每日上限读取每用户消费的同一种方式读取 (org, customer) 的尾随消费。

拒绝必须是它自己的错误 `customer_budget_exceeded`，body 里带上限和周期。构建者的产品需要给**他们的**用户显示一个干净的"你已达到你的套餐上限"消息，而不是一个关于别人余额的 treg 错误。绝不要在这个响应里包含组织的总体余额：那是构建者的私有数字，而该响应可能被展示给他们的客户。

一个 `status: blocked` 的客户被直接拒绝 —— 撤销的软版本，不需要 token 管理。

### 第 3 块 —— 用量端点（导出）

    GET /orgs/{id}/usage?group_by=customer&from=...&to=...
    -> [{customer, calls, charged_micro, by_provider: {...}}, ...]

聚合模式已经存在于 `reconcile.provider_spend`（审计行，30 天窗口）；这是同一个查询，只是不同的 group-by 和一个日期范围。现在 JSON；如果构建者要求以后再来 CSV。这个输出就是构建者据此开票的东西。

### 隔离模式：每客户一个 token（已存在）

标签计数；token 控制。对于需要真正控制的客户，构建者为他们铸造一个专用 agent token：`POST /orgs/{id}/agents` —— 已经端到端存在。

| 需求 | 标签够吗？ | 需要 token 吗？ |
|---|---|---|
| 用量计数、预算、开票 | 是 | 否 |
| 立即切断一个客户 | `status: blocked` 可用 | 撤销也可用 |
| 每客户不同的工具访问（高级 vs 免费层） | 否 | 是 —— 每成员 `tool_access` 已存在 |
| token 跑在**客户**设备上（泄漏 containment） | 否 | 是 |

文档规则：**计数用标签，控制用 token。** 所有人从标签开始；少数几个升级。

一个粘合任务：用每客户 token 发起的调用应当**无需袋**就归因到该客户 —— 从一个成员资格上的 `customer` 字段设置 `meta.customer`（成员资格上可空的列，当 agent 用 `--customer cust_8123` 铸造时设置）。这样两种模式产生一份一致的用量报告。

## 三个陷阱，在设计时发现的 —— 不要跳过

1. **每成员每日上限会节流整个客户群。** 所有被标签的流量骑在一个成员资格上，所以一个成员的 $5/天上限变成了全产品的天花板。构建者组织需要那个上限可抬高（按成员覆盖在精神上是 `unmetered` 成员已存在；干净的修复是一个每成员资格 `daily_cap_micro` 覆盖列）。没有这个，构建者付费撑不过它的第十个客户。
2. **幂等性必须按标签作用域。** 构建者的两个客户**会**都在共享 token 下发送 `retry-1`。`IdempotentCall` 今天在 `(membership_id, key)` 上唯一；它必须变成 `(membership_id, customer, key)`，其中 `customer` 默认 ""。注意：这是一个对既有唯一约束的 ALTER —— `create_all` 不会做；生产是 Postgres，部署里需要一个真正的迁移步骤。
3. **为什么不每客户一个组织**（诱人的捷径）：构建者的余额会碎成 N 个分别充值的罐子，他们的密钥需要复制进每个组织，而 $1 的促销赠金会乘 N —— 一台免费额度印刷机。被拒绝；不解决这三个就别再提。

## 顺序，每步之后停一下

1. 袋：接受 `X-Treg-Meta` 头 + MCP 的 `meta` 参数，记录进审计 telemetry + 账本 meta。只做归因，不执行任何东西。测试：被标签调用带着所有键落进两个记录；未标签调用与今天逐字节一致；第 6 个键被清晰错误拒绝。
2. 用量端点。测试：分组、日期范围、零消费的标签不出现、以及组织隔离（组织 A 不能读组织 B 的用量 —— 多租户测试模式）。
3. `CustomerBudget` + 执行 + `blocked`。测试：上限拒绝形态、错误永不泄漏组织余额、blocked 被拒绝、无上限客户不受影响。
4. 幂等性作用域 + 该约束的 Postgres 迁移。
5. 成员资格 `customer` 字段 + agent-new 上的 `--customer`（隔离粘合）。
6. 每成员资格上限覆盖。
7. 文档：llms.txt（一个"for builders"章节）、`docs/context/architecture/multi-tenancy.md` 和 `money.md` 片段、MAP.md 条目、skill.md 变了就重新生成 skill。

步骤 1–3 就是产品；4–6 是正确性与规模；每一步都可单独发布。

## 复用记分板

复用：组织、账本 reserve/settle、审计、每日上限插入点、OAuth 服务器（客户付费模型）、公开 demo 先例（它已经用同一个共享 token 按 IP 计量许多匿名用户 —— 这是同样的机制，只是把颗粒改成客户 id）、agent token、每成员 ACL。

真正全新：一张表、一个头（meta 袋）、一个端点、两列、一个迁移。

## 可能出什么错，先去哪看

- **预算检查与自己竞态** —— 两个并发调用都在上限内，合起来超了。和每次 reserve 竞态同类；v1 可接受（上限是软业务限制，不是账本不变量），但在代码注释里说明，而不是等它被当作 bug 发现。
- **用量端点性能** —— 每组织的审计行可能很大；该查询需要既有的 org+created 索引加一个 telemetry-tag 策略（最坏情况，以后来一个小的反规范化 `customer_spend` 每日汇总；在它真的痛之前别建）。
- **标签基数滥用** —— 一个失控的集成每次调用都发一个全新的 UUID（作为任意键的值）会撑大报告。每键每组织限制不同值个数（比如 10k），用清晰错误，在预算创建和报告时便宜地计数。
