# 幂等调用 —— 一次重试不能计两次费

**状态：**已规划，待批准。尚未构建。

## 引发它的那个问题

> "结果定价如何处理重试，agent 在这之前需要幂等计费才能工作"

公开问的，而且正确。agent 比人重试得多得多，所以这对 treg 不是边缘情况。它就是主要的流量模式。

## 什么已经能工作，所以我们不重建它

大多数重试现在已经是免费的，这很重要，因为它告诉我们真实的缺口有多窄。

| 结果 | 计费了吗？ |
|---|---|
| 5xx、3xx、网络错误、上游超时 | 从不 |
| 4xx | 仅在 `per_call` 下，即供应商为接受请求而计费 |
| 2xx | 是 |

所以常见情况 —— 一个 agent *因为出了错*而重试 —— 今天不花额外钱。`_platform_billable` 已经划了那条线。

结果定价也基于供应商自己上报的费用而不是我们的估算（`_observed_cost_micro`）结算，所以一个什么都没找到的 Hunter 查询是免费的，账本记录真实数字。1,362 个端点是 `per_success`、120 个是 `per_result`，所以这是目录的大多数。

## 真实的缺口

一个情况，且仅一个：

1. treg 调用供应商
2. 供应商成功，并向我们计费
3. 响应在返回 agent 的路上丢了，或者 agent 自己的客户端超时了
4. agent 重试
5. treg 再次调用供应商并再次计费

从 treg 这边看，这两个是两次成功的调用，之间没有任何关联。钱是真的：我们付给供应商两次，并向团队收两次。

`ledger.topup` 已经有一个幂等键正是为此（`Stripe redelivers webhooks`）。`/call/` 没有。

## 只做到不重复计费还不够

廉价版本是记住一个键已经被计费过，然后跳过第二次收费。它是错的，而且值得说清为什么：treg 仍会发起上游调用，所以**我们仍然付给供应商**。我们会把双倍成本从客户身上挪到自己身上，而不是消除它。

真正的幂等意味着第二次请求永远到不了供应商。这需要存储第一次的响应并回放它，那就是 Stripe 模型，也是唯一真正解决问题的版本。

## 设计

### 键来自客户端，否则什么都不发生

`/call/` 上的 `Idempotency-Key`。没有键意味着与今天的行为完全一致：不存储、不查找、不改变。这是刻意的。一个服务端发明的键（比如对 URL 和 body 哈希）会静默地把调用方真正想做两次的两个调用合二为一，而"把这个发两次"是一个 API 合理的诉求。

### 作用域：仅计量调用

一个团队用**自己的**密钥调用是他们的账单和他们与供应商的关系。treg 没道理缓存那个，而且存储那些响应意味着为了一个对谁都没好处的理由而持有别人的数据。

### 只存储成功的、已计费的响应

失败已经是免费的，所以没什么需要保护。这正是让存储有界的原因：我们只为真正花钱的调用保留 body。

### 24 小时窗口

重试发生在几秒内。一天是宽裕的、常规的、且易于推理的。一行过了它的窗口就简单视为不存在，调用正常进行。

### 表

`IdempotentCall`：`(org_id, key)` 唯一，外加 `endpoint_id`、请求指纹、存储的状态和 body、`charged_micro`，以及 `expires_at`。

`(org_id, key)` 而不是仅 key：键是客户端选的，两个团队终将冲突，而跨租户边界的冲突会把一个团队的数据提供给另一个。这里是唯一一个会成为安全事件而不是计费 bug 的失败。

### 请求指纹防范键复用

一个客户端为*不同*请求复用同一个键是犯了错，而静默返回旧响应会把它藏起来。存储一个 (endpoint, method, body/query) 的哈希并比较。不匹配时，用 `422` 拒绝并说明该键已用于不同请求。Stripe 也这么做，而响亮的失败是有用的那个。

### 并发：由数据库决定

两个重试可能同时到达，且两者都可能错过查找。`(org_id, key)` 唯一约束正是让它安全的东西：先插入一个**占位行**，那场竞速的输家等赢家，而不是发起第二次上游调用。

这和 `ledger.reserve` 里条件 UPDATE 以及"先删后验证"的授权代码是同样的推理：在两条路径都可能写之前读的地方，必须由数据库做仲裁。Python 里的"先检查后行动"会留下这道特性本要关闭的窗口。

### 调用方看到什么

一个被回放的响应带一个说明这一点的头，连同原始收费。一个静默返回缓存 body 的重试会与一次新调用无法区分，而一个向人报告成本的 agent 应该能说"这是回放的，没花额外钱"。

## 顺序

1. 表，以及 `(org_id, key)` 唯一性。还没有行为。
2. 读路径上的查找与回放，带指纹检查。存储仍关着。
3. 写路径上存储，仅针对计量的成功。
4. 占位行与并发重试竞速。
5. 过期，以及一个清理窗口外行的 reaper。
6. **停下并证明它**：用同一个键对真实端点开两次火，确认供应商被调用一次、账本移动一次、两个调用方都拿到同样的 body。

## 可能出什么错，以及我会先去看哪

- **跨租户键冲突。** 由复合键覆盖，而且这是我第一个会写的断言，因为它是这里唯一泄漏数据而不是钱的失败。
- **存储了我们不该存的 body。** 仅计量和 24 小时是限制。任何拓宽其中之一的都应该被显式论证。
- **价格变了之后的回放。** 存储的 `charged_micro` 是真正收走的数；回放不收费，所以这在构造上一致。还是值得一个测试。
- **大小。** SERP 和 scrape 响应并不小。如果存储成为问题，答案是一个超过它就不存储的大小上限，而不是更短的窗口，因为一个大到无法缓存的调用正是其重试最可能已超时的那个。
- **蔓延成通用缓存。** 这是一个重试守卫，不是响应缓存。它绝不能服务一个没带相同键的请求，否则它不再是正确性特性，而开始是陈旧数据。

## 诚实的体量评估

比 OAuth 工作小：一张表、一次查找、一次存储、一次竞速。用心放在租户边界和并发上，而不是代码量。对不发键的任何人，既有行为完全不动，这让爆炸半径很小。
