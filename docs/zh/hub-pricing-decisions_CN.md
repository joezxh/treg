# hub 定价灵活性 —— 那些决策

今天一个 hub 工具只有一个价格：制作者设定的一个固定 `price_usd`，运行成功时扣一次，作为一块 `earned` 付给制作者。买家还支付每个目录步骤的真实成本；一个步骤在制作者自己的工具上跑时用的是制作者的密钥，不被计量。这项工作加两种更多定价模式，让价格可以随运行变化。

这个文件是 2026-09-14 与 owner 的一次问答记录，在任何设计工作之前。问题逐字保留。每个问题下面是 owner 批准的回答。

## owner 设定的框架
- 给 hub 加定价灵活性。固定价格不够。
- 另外两个问题（`data.csv` 是什么、脚本在哪跑）是理解，不是缺口。关于 `data.csv` 或沙箱没有任何改变。

## 第一轮 —— 定价模型

**1. 除了固定价格，我们加哪些定价模式？**
加两个，保留固定。模式 `flat`（今天）。模式 `per_unit`：一个价格乘以脚本返回的一个计数。模式 `cost_plus`：制作者赚运行目录步骤成本的一定百分比。制作者为每个工具版本选一种模式。

**2. 在 `per_unit` 模式下，一个单位是什么？**
脚本在一个保留输出字段 `units` 里返回一个整数。treg 用 `units` 乘以每单位价格。制作者的代码设 `units`，通常是行数，但可以是任何他们计费的东西。

**3. 一个可变价格的工具是否声明每次运行的最高价格？**
是，必填。manifest 为 `per_unit` 和 `cost_plus` 加 `max_price_usd`。这是买家为一次运行的价格部分能付的最多。

**4. 价格开始时未知时我们怎么hold钱？**
开始时预留 `max_price_usd`，运行，然后结算真实价格并释放其余。这保持"先预留再结算"的规则恰好一次，而且买家的最坏情况在运行前就已知。

**5. 在 `cost_plus` 模式下，制作者的价格基于什么？**
制作者设 `markup_percent`。制作者赚运行目录步骤成本的那个百分比。例：步骤成本 $0.20，加成 30%，制作者赚 $0.06，买家为运行付 $0.26。

**6. 制作者在哪写模式和它的数字？**
`recipe.json` 得到一个 `pricing` 块：`{mode, price_usd, per_unit_usd, markup_percent, max_price_usd}`。treg 只读该模式需要的字段。一个只有 `price_usd` 的文件仍意味着 `flat`。

**7. 买家在公开页面上运行前看到什么？**
页面用文字展示模式和最坏情况。`flat`："$X / 运行"。`per_unit`："$X / 单位，每次运行最多 $Y"。`cost_plus`："供应商成本加 Z%，每次运行最多 $Y"。

**8. 一个可变运行成功时，制作者怎么被付？**
和今天一样。最终的可变价格在和今天同一个事务里作为一块 `earned` 结算给制作者。没有新的钱条目。

**9. 在 `per_unit` 里，什么阻止一个巨大的计数收取一个巨大的价格？**
真实价格是 `units × per_unit_usd` 和 `max_price_usd` 中较小的那个。制作者永远赚不到自己声明的上限之上。这也正是让预留上限安全的东西。

**10. 既有的固定价格工具有任何改变吗？**
不变。一个只有 `price_usd` 的 recipe 保持 `flat`，预留和结算完全像今天。新模式通过 `pricing` 块选择加入。

## 第二轮 —— 边角

**1. 如果一个 `per_unit` 脚本不返回 `units`，或返回坏值，适用什么价格？**
运行以一个清晰错误失败，制作者什么也赚不到。`units` 必须是 0 或更大的整数。一个 `units` 为 0 的运行成功并收 0。缺失或不是整数使运行失败。

**2. 当一个工具不调用任何目录步骤时，`cost_plus` 被允许吗？**
发布时拒绝。如果模式是 `cost_plus` 且 `uses` 没点名任何目录 id，发布带一条消息失败。那个制作者应该选 `flat` 或 `per_unit`。

**3. 发布如何给 check 运行定价？**
不变。check 运行跳过价格部分，和今天一样。它只证明工具能跑并返回它声明的字段。它从不收价格。

**4. check 验证的是价格字段，不只是输出字段吗？**
是。manifest 校验器一开始就检查 `pricing` 块：模式有效、模式需要的数字都在、`max_price_usd` 至少是每单位价格。对 `per_unit`，check 运行也要求输出里有一个整数 `units`。一个价格坏掉的工具永不上线。

**5. 收入报告是否加一列给可变价格？**
加一列，`avg_price_micro`，赚得金额除以成功运行数。没有每单位细分，只是每次成功运行的平均价格，让制作者看到可变价格落到哪。

## 第三轮 —— 标题（2026-09-18）

**1. 调用方首先读什么价格？**
一个范围，不是公式。"steps +25% up to $0.5/run" 准确但不可读。每个界面（控制台列表与概览、`treg hub ls`、公开页面、`catalog_get`、搜索行）上的标题是成功运行实际花了什么，步骤和卖家价格合在一起，在过去 30 天：当每次运行花费相同时是一个数字，否则 `$low–$high/run`。公式作为第二行保留，给制作者（`price_label`）。

**2. 谁的运行计入？**
每次成功运行，制作者自己的和定时的检查都算：不管谁调用步骤成本相同，否则一个新工具在陌生人付钱前会什么都不显示。一个制作者没付价格的运行，其卖家部分从定价块和它的步骤成本推导（`seller_part_micro`）；一个调用方的运行用他们付的价格。最小-最大，不是修剪过的带：一个选了贵模式的调用方应该看到它。

**3. 在任何运行之前？**
制作者的价格，费用未知："$0.15/run + 供应商费用"、"$0.02/result + 供应商费用"、"供应商费用 + 5%"、"免费 + 供应商费用"（当工具只调用制作者自己的工具时没有 "+ 供应商费用"）。`price_samples` 说明标题建立在多少次运行上。

**4. 制作者的措辞，且没上限。** 模式改名为制作者会说的：`per_call`（曾是 `flat`）、`per_result`（曾是 `per_unit`，计数是 `results`，仍读 `units`）、`percent`（曾是 `cost_plus`，字段是 `percent`）。制作者读 "$0.15 per call"、"$0.02 per result"、"5% of provider fees"；短语 "steps +25% up to $0.5/run" 消失了。`max_price_usd` 不再必填：它是 runner 需要一个最坏情况来 hold、伪装成一个定价字段。hold 现在从约束运行的东西推导：对 `percent`，调用方的上限（费用 + 部分 ≤ 上限）；对 `per_result`，`results_from` 输入的值。制作者仍可声明一个更低的上限。旧名字验证并规范存储，所以没有已发布的工具改变。

**5. 没构建：全包定价。** 一个想要吸收供应商费用的一口价（"$1.00 per run，供应商我来付"）的制作者没有模式；调用方总是直接付步骤。那会让一个 hub 工具看起来像产品而不是加成，而且它改变钱的流向（制作者需要余额来服务调用）。列入积压。

## 第四轮 —— 每种一个规则（2026-09-24，owner + Jason）

Jason 对制作者页面的评审问：一个脚本能自己说价格时，为什么需要三种定价模式。决定：

**1. 一个脚本用 `ctx.charge` 在一个声明的上限下给自己定价。** `"pricing": {"max_price_usd": N}` 和 run.js 里的 `ctx.charge(usd, note)` 行：一笔手续费、每结果、一次调用的 `cost_usd` 上的加成、一个供应商的成本。上限是调用方在运行前看到的，也是 runner hold 的；运行以各行之和结算。上限保留是因为调用方读不了代码：没有它，价格只在运行后才知道。

**2. 一个步骤 recipe 保持一个固定价格**（`"pricing": {"price_usd": N}`）：它没有代码去调 `ctx.charge`。可变价格意味着一个脚本。

**3. `per_result`、`percent` 和 `max_charge_usd` 连同旧别名被移除。** hub 在生产是关的，所以没有已发布的工具需要它们；示例工具和演算过的 recipe 被改写成 `ctx.charge`。`results_from` 和 `results` 输出字段不再给任何东西计费。
