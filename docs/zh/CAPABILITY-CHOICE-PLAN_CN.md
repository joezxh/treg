# 能力选择 —— agent 决定，treg 只让事实成真

**状态：**已规划（2026-08）。取代落地页支柱 2 的"treg 替你路由"读法。

## 那个承诺，以及它真正需要什么

落地页说：*"你的 agent 要的是任务，不是工具……treg 知道每个场景的阶梯，并把每次调用路由到那个还在线的最佳选择"* —— 带着 *内置的故障转移*、*实时对比*、*随时 pin 一个供应商*。

按一种读法，那意味着 **treg** 挑供应商，并在失败时静默切换。我们测算了那要花什么代价：

| | |
|---|---|
| 由 treg 持有密钥、2 个以上不同供应商提供服务的能力 | **171** |
| ……其中请求形态在各供应商间已经一致 | **5** |
| 一个能力内的价格跨度 | 高达 **261×**（`companies.enrich`：$0.0015 → $0.39） |

所以 171 个里有 166 个在 treg 能把一次调用重发到别处之前，需要一个**翻译层** —— 每个能力一套规范输入 schema，加上每端点的映射 —— 而 `capabilities.yaml` 是一份分类法（`id: description`），所以这类数据一条都不存在。

而且翻译不是真正的问题。**这些端点问的是不同的问题：**

| 端点 | 需要 |
|---|---|
| `hunter.people.email.find` | `domain` + `first_name`/`last_name`（GET，query） |
| `leadmagic.people.email.find` | `first_name`、`company_name`、……（POST，body） |
| `leadmagic.x.b2b-profile-email` | 一个 **`profile_url`** —— 完全不同的信息 |

一个按价格选的路由器会给一个拿着名字和域名的调用方挑第三个，然后失败。

## 决策：agent 选择；treg 发布事实

agent 知道**它实际拿到了哪些输入** —— treg 不知道。它也不需要翻译层，因为它从目录读取所选端点自己的参数并构造那个请求。所以把工作交给本来就握有上下文的一方，难题就消失了。

这也让创始规则完好：treg **转发，绝不建模**。一个路由器本会是第一个打破它的特性。

treg 作为交换所欠的，是**只有 treg 能做的**那部分：它看到每一次调用、来自每个租户，所以它能说哪些端点真的能用、多快、以及它们真的收多少。那正是把"实时对比"从文案变成事实的东西。

## 三块

### 1. 发布每个端点的观测现实

**冷启动是难的部分，而钱解决不了它。** 第一天这些端点的 `CallRecord` 都是空的，所以每个格子都会读成 `—`。三个来源填它，而它们必须保持视觉上可区分 —— 把一次测量和一次声称平均掉，就毁了测量的价值：

| 来源 | 覆盖 | 成本 | 它诚实地说什么 |
|---|---|---|---|
| 目录自己的 `verified:` 戳 | **1,810 个合格端点里的 1,380 个**（76%），都在上个月内盖的戳 | **免费，今天** | "我们手工跑过它，它答了，N 天前" |
| 供应商状态页 | ~40 家供应商（我们付费的 3/3 都有；ScrapeCreators 按**端点**发布） | 免费，一次性研究 | "供应商说它现在在线" |
| 我们自己的 `CallRecord` | 随真实使用增长 | 见下 | **"这里是真正发生的"** |

只有第三个是测量。所以 `LAST OK` 列在真实调用产生它时打印一个裸年龄，而在它来自戳时打印一个 **`✓` 年龄** —— 一眼就把证据和一个带日期的声称分开。

**种子扫描的上限由账户决定，而非由钱决定。** `scripts/catalog_verify.py` 已经发送每个端点的 `test_request` 并检查状态；它只是丢弃了计时。但它只能调用我们持有密钥的供应商，而生产持有**三个**：

| | 可调用端点 | 每个 5 次调用 | 我们真能**对比**的能力 |
|---|---|---|---|
| 我们今天的密钥（tikhub、dataforseo、scrapecreators） | 351 | **$7.50** | **157 个里的 68 个** |
| 若 16 个密钥位都填满 | 526 | $26.90 | 157 个里的 157 个 |

$7.50 不算什么；约束在于对比九家邮箱查找供应商需要九个里各开一个付费账号。而且对比需要两边：在 89 个我们恰好持有一个供应商密钥的能力上，一次扫描只产生一个数字夹在两个破折号之间 —— 一则给我们付费的唯一供应商的广告，而不是一个选择。**所以 treg 买哪些供应商的账号是一个业务决策，而且它和决定 treg 到底能为哪些能力做无密钥服务的是同一份清单。**

`CallRecord` **已经记录**了需要的一切，自市场发布起就是：`endpoint_id`、`status_code`、`duration_ms`、`response_bytes`、`cost_observed_micro`、`cost_estimated_micro`、`params_hash`、`created_at`。没有新东西要收集 —— 只需聚合。

每个端点，在一个滚动窗口上：**成功率**、**p50/p95 延迟**、**观测-vs-估算成本漂移**、**上一次应答的时间**，以及**样本量**。样本量不是装饰：两次调用上的 100% 成功率绝不能排在四百次上的 97% 前面，而读者必须能看到这一点。

展示在已经做出选择的地方 —— `treg catalog get <id>` 今天就会列出一个能力的备选，所以这些数字属于那些行 —— 以及通过 API 给 agent。

沿用 `reconcile.py` 的先例：查询时、只读、admin 级窗口、聚合在 Python 里做，因为溯源信息在一个 JSON 列里。

### 2. 教会决策流程

在 `skill.md` 和 `/llms.txt` 里，作为一条 agent 可遵循的有序规则：

1. **匹配你拿到的输入。** 一个要 `profile_url` 的端点，在你拿着名字和域名时不是替代品，不管它多便宜。
2. 然后优先 **verified** 而非未验证，然后 **成功率**（把样本量纳入视野），然后 **价格**。
3. 遇到 **429 / 5xx / 超时**，试下一个供应商 —— 你知道它的参数，所以你能构造它的请求。
4. **绝不重试一个你造成的 4xx。** 修参数是正解；在别处重试只会为一个错误在 N 个供应商上烧钱。
5. **花钱之前先告诉人价格**，动用团队的余额之前。

### 3. 用团队策略约束它

一个组织可以为一个能力 **pin** 一个供应商，或 **deny** 一个，于是 agent 的自由止于团队的决策开始之处。pin 也是让选择对 CI 确定的东西。复用既有的 deny-rule 机制，而不是发明第二个策略引擎。

## 刻意以后再做

**自动选择（`--auto`）** 给不是 agent 的调用方 —— 一个 `curl`、一个 CI 任务、一个人。一旦 (3) 存在，一个 pin 已经为常见情况做了这件事。跨供应商*翻译*保持不在范围内，直到一个能力的规范 schema 值得手工写，而且即使那时也只对价格跨度最广的那一小撮。

## 文案因此改变

落地页的 *"✓ 你的 agent 从没挑过供应商 —— treg 路由了它"* 在这个设计下变成假的。诚实的说法更接近 *"你的 agent 从实时数据 —— 价格、成功率、延迟 —— 里做了选择，而不是瞎猜。"* 在 (1) 和 (2) 上线之前，`llms.txt`、`skill.md` 和 charter 里已有的措辞仍然成立：**treg 对比，选择是调用方的，没有自动故障转移。**
