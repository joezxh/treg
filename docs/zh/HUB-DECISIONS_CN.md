# 工具 hub —— 那些决策

工具 hub 让一个制作者把他们已有的某样东西变成一个别人家的 agent 也能调用的工具：他们自己的数据（Supabase、Google Sheets、一份粘来的 CSV）、他们自己的路由逻辑，或者一份目录工具的组合。两种 recipe：一个 JSON 步骤文件，或者一个脚本。脚本在一个沙箱里运行，只通过 `ctx.call` 抵达制作者的 treg 账号：制作者已注册的工具、按名字引用的凭据、他们的 credit。绝没有人把密钥粘进脚本。该工具立刻可被 API 和 MCP 调用，带一个可分享的 URL，且制作者设定一个价格。

这个文件是 2026-09-09 与 owner 一次问答的记录，在任何设计工作之前。它跟在 owner 与 Jason 于 2026-09-08 的会面（路线图的唯一事实来源）之后，并扩展了 `docs/RECIPES-DECISIONS.md` 里更早的 recipe 决策、且在若干处覆盖了它们。**问题逐字保留。** 每个问题下面是 owner 批准的回答。owner 在问题没问到的地方补充了东西的，写在"The owner added"下。

目的：下面没有任何设计决策建立在猜测上。

---

## owner 设定的框架

- 这不是原型。这是 MVP，是真实的系统。我们用 Mitchel 测它，然后定稿并把它上线。
- 从一开始就两种 recipe：一个 JSON 步骤文件，或者一个脚本。
- 案例研究是数据：一个脚本连到制作者的 Supabase 或 Google Sheet，或者一份粘来的 CSV，并用输入参数（筛选、搜索、限制）提供数据。
- 一个脚本拿到制作者的 treg 上下文：他们所有的工具、他们自己的 credit、他们自己的凭据，按名字引用。他们从不下写任何凭据。
- 整个东西从第一天起就是 MCP。他们的 agent 创建工具并立刻拿回 API 调用，调用方的 agent 也立刻调用它。
- 来自 2026-09-08 的会面："just serve"是无许可的、立刻上线；进入发现（discovery）的上架需要一次 pull request 和验证。制作者设定价格并赚取 credit。

**owner 最后补充：**面向 agent 的文件必须告诉 agent：如果你用了一个尚未进入系统的新凭据，不要硬编码它。先用另一个工具创建它（注册 secret 或工具），然后再用它。

## 第一轮 —— 边界

**1. 数据工具是它自己的模板系统，还是我们写的一个脚本 recipe？**
MVP 里没有模板系统。treg 为每种来源（Supabase、Sheets、CSV）各写一个脚本 recipe。制作者填它的输入。

owner 补充：模板的想法是为以后更多数据提供商准备的。这个 recipe 没有模板；它只是一个脚本。

**2. 沙箱从第一天起就存在吗？**
是。一个我们控制的、独立的短生命进程，带内存与时间上限、没有网络。

**3. 脚本如何连到制作者的 Supabase？**
制作者把 Supabase 注册为一个自有工具（base URL + key），完全像今天一样。脚本用 `ctx.call("supabase/rest/v1/leads?...")` 调用它。沙箱保持无网络；`ctx.call` 是唯一的出路。

**4. 脚本会看到 secret 的值吗？**
绝不。secret 只通过团队的已注册工具、在 `ctx.call` 内部传输。没有 `ctx.secret(name)`。

**5. 卖家的钱去哪？**
全额落在卖家的团队上，作为一种新的 credit 块类型，`earned`。立刻可作为 treg credit 消费。提现是积压项。

**6. 粘来的 CSV 存在哪？**
treg 存它，每个工具上限 50 MB，上传后只读。同一个数据脚本提供它。替换文件会生成一个新版本。

**7. 原型里有什么被上架吗？**
MVP 里的所有东西都是 live-but-unlisted：可通过 id 和 URL 调用，不在搜索里。上架路径（pull request、验证）在 MVP 之外。

**8. 制作者在原型里如何创建工具？**
先走 agent 路径：创建、测试、给工具定价的 API 加 MCP 动词，以及一个展示现状的最小仪表盘页面。富界面来自之后的 mockup。

owner 补充：这是 MVP，不是原型。API 和 MCP 都要，立刻测试，然后定稿上线。

**9. 一个 hub 工具的 id 在调用路上长什么样？**
点号分隔，像目录 id：`mitchel.leads-db`。handle 是第一段。没有斜杠，所以不与自有工具解析冲突，且对 MCP 友好。

**10. 数据案例研究声明哪些输入？**
四个：`select`（列）、`filter`（`column=value` 对）、`search`（一个文本字段）、`limit`（int，默认 20，最大 100）。第一版没有别的。

## 第二轮 —— 脚本契约与运行

**1. 脚本的文件和语言是什么？**
`run.js`，一个默认的 async 函数，由一个嵌入式 JavaScript 引擎在子进程里运行（QuickJS）。没有 Node，没有 npm，没有 import。

**2. 自有工具的 `ctx.call` 和一次目录调用形态相同吗？**
一个函数，三种 target 形态，和今天的 `/call/` 相同：一个目录 id、`<tool>/<path>`，或者一个完整 URL。`ctx.call(target, {method, query, body, headers})`。它返回 `{status, headers, json, text}`。

**3. manifest 必须点名脚本会用到的团队工具吗？**
是。`uses` 接受目录 id 和自有工具名。一次在列表之外的 `ctx.call` 会被拒绝。

**4. 脚本可以返回什么？**
一个 JSON 对象，最多 2 MB。manifest 声明它的顶层字段；runner 检查它们存在，否则拒绝运行。

**5. 运行自身的计算成本去哪？**
MVP 里不计费。调用方付步骤加上卖家的价格。在我们了解数字之前，计算是我们自己的。

**6. 脚本的运行上限是什么？**
和一个 JSON recipe 相同：120 秒墙钟、20 次 `ctx.call`、64 MB 内存、每团队 4 个并发运行。

**7. 脚本能打日志吗，谁读它？**
`ctx.log(text)`，50 行，每行 2 KB，在运行记录上保留 30 天。制作者看自己工具的日志；调用方只看 trace，不看日志。

**8. 当制作者的 Supabase key 在生命周期中途被撤销时会发生什么？**
该步骤失败，运行随 trace（点名工具）一起失败，调用方对该失败步骤不付费、对卖家的价格也不付费。连续 3 次运行失败后，健康状态把工具标为 failing。

**9. 脚本针对制作者的团队还是调用方的团队运行？**
自有工具和 secret 针对制作者的团队，钱和身份针对调用方的团队。一次运行同时携带两者：它花调用方的余额，用制作者已注册的 key。

**10. 在它上线前我们测试脚本吗？**
是，在创建时：制作者提供 `check.json`（样本输入加必需的输出字段），treg 在制作者自己的余额上真实地跑一次，只有当它通过才上线。

## 第三轮 —— 价格与钱

**1. 卖家如何声明价格？**
manifest 里一个字段：每次成功运行 `price_usd`，允许小数（`0.01`）。treg 为他们展示每千次的一行。零意味着免费。

**2. 调用方一次运行总共付多少？**
卖家价格加上每个被计量的步骤，trace 里各一行。目录页两者都展示："seller $0.01 + steps from $0.003"。

**3. 卖家何时被支付：仅成功时？**
仅在一次成功运行时。一次失败的运行不付卖家任何东西；调用方只付完成的步骤。

**4. treg 从卖家的价格里抽成吗？**
MVP 里不抽。卖家价格的 100% 作为 `earned` credit 落在卖家团队上。平台费是以后一个决定，在开始之前宣布。

**5. earned credit 能付卖家自己的步骤吗？**
能。`earned` 是普通的、可消费的余额。它在促销 credit 之后、购买 credit 之前被消费。

用 owner 要求的平实语言：当有人运行 Mitchel 的工具并付他的价格时，那笔钱作为 credit 落在 Mitchel 的 treg 余额上，在一个标着 `earned` 的块里。它和 $1 欢迎 credit 或 $10 充值属于同一种余额。他可以立刻把它花在任何 treg 调用上，包括他自己 recipe 里的目录步骤。他唯一还不能做的是把它提现为现金。消费顺序是促销优先、earned 其次、购买最后。

**6. 创建时谁来付 check 运行？**
制作者自己的余额，按正常步骤价格，不收卖家价格。创建一个你连跑一次都付不起的工具，会被以所需金额拒绝。

**7. 卖家的价格走预留-结算像一步吗？**
是。运行时开头开一个额外的 hold `{run}:price`，成功时结算给卖家，失败时释放。同样的原语，没有新的钱路径。

**8. 制作者能改一个在线工具的价格吗？**
能，任何时候；它适用于改动之后的运行。trace 盖上所付价格的戳。改价不改变版本号。

**9. 调用方在一个 hub 工具上有上限吗？**
有，既有 header `X-Treg-Run-Max-Cost`，默认 $1.00，涵盖卖家价格加步骤。运行在会越过它的那一步之前停下。

**10. 卖家能看到谁调用、付了多少吗？**
一个每工具的收益视图：运行、成功计数、earned 总额，按天。不展示调用方身份；只有计数和金额。

## 第四轮 —— 制作者的路径：创建、分享、MCP

**1. 制作者如何通过 API 创建一个工具？**
`POST /hub/tools`，用同样的四个文件作为字段：`manifest`、`script`、`check`、`readme`。和文件夹同形态，一个请求。CLI 和 MCP 发同样的 body。

**2. 制作者的 agent 得到哪些 MCP 动词？**
`/mcp/` 上三个新工具：`hub_create`（上面的请求，跑 check，返回在线 id 或失败）、`hub_update`（新版本）、`hub_mine`（列表、健康、收益）。调用仍是既有的 `call`。

**3. 调用方的 agent 需要用 hub 工具要什么新的东西吗？**
不需要新东西。`call("mitchel.leads-db", {...})` 就能工作。未上架工具不出现在 `catalog_search`；对一个已知 id 的 `catalog_get` 返回它们。

**4. "分享 URL"到底意味着什么？**
每个工具一个公开页面：`treg.to/hub/mitchel.leads-db`。它展示 readme、输入、价格、健康，以及精确的一行 `call`。读它无需登录；调用它需要 token 和余额。

**5. 谁可以调用一个未上架的工具？**
任何有 treg token 和余额的人，如果他们知道 id。未上架意味着不在搜索里。一个 private-to-my-team 开关是积压项。

**6. id 里的 handle 是什么？**
团队 slug。一个工具属于一个团队，而不是一个人；slug 已经唯一、且已经在 URL 里。

**7. 一个 hub 工具能在 `uses` 里点名另一个 hub 工具吗？**
仍然不行。`uses` 只接受目录 id 和制作者自己的工具。深度一层。

**8. 制作者如何更新一个在线工具？**
`hub_update` 跑 check，并在通过时发布版本 N+1；最新版默认服务；`id@N` 固定。旧版本在一个更新的版本存在后 30 天内仍可调用。

**9. readme 有要求的形态吗？**
自由 markdown，最多 4,000 字符，外加 manifest 的 `summary`（200 字符）在每个列表里展示。summary 是 agent 最先读的东西。

**10. 调用方在一个 hub 工具 424 步骤失败里看到什么？**
步骤名、工具自己的名、状态，永不展示上游 URL 或错误 body。制作者在自己的运行日志里看到完整错误。

## 第五轮 —— 界面

**1. 哪个界面是主界面？**
MCP 上的 agent。CLI 一一镜像它。仪表盘展示并编辑 agent 做出的东西。每个屏幕都有一个 agent 等价物。

**2. CLI 命令族是什么？**
`treg hub init <name>`（脚手架出四个文件）、`treg hub run . --input k=v`（针对真实 API 本地运行）、`treg hub publish .`（创建或更新）、`treg hub ls`、`treg hub earnings <id>`、`treg hub logs <id>`。

**3. MVP 里仪表盘得到一个构建器，还是仅一个查看器？**
仅一个查看器和轻量编辑。一个 Hub 页列出我的工具；每个打开一个含 readme、输入、价格（可编辑）、健康、收益、运行日志的页面。没有脚本编辑器。

**4. 制作者的 agent 如何被教会 hub？**
`skill.md` 和 `llms.txt` 里一个新章节，随 runner 一起发布的同一 PR 加入。它教：init、四个文件、`ctx.call`、check、发布、定价、分享 URL。

owner 补充：该章节还必须说：如果你用了一个尚未进入系统的新凭据，不要硬编码它。先用另一个工具创建它，然后再用它。

**5. 面向 agent 的设置在端到端上看是什么样？**
agent 注册 Supabase 工具、写四个文件、跑 `hub_create`、读 check 结果、返回分享 URL 和那行 `call`。五个 agent 动作，没有人参与。

**6. 调用方在哪找一个 hub 工具？**
分享 URL、按 id 的 `catalog_get`，以及 `treg catalog get <id>`。被上架的工具出现在搜索里，带一个 `HUB` 标记和卖家价格（在步骤价格旁边）。

**7. 公开工具页展示什么、隐藏什么？**
展示 summary、readme、输入表、输出字段、价格行、健康点、版本、那行 `call` 示例，以及 check 的运行 trace。隐藏脚本、制作者的工具、和每个 key。

**8. MVP 里存在运行页吗？**
存在，给调用方自己的运行：`/app/runs/<run_id>` 带 trace 和成本。运行时轮询是积压项；MVP 展示已完成的运行。

**9. 制作者的收益视图展示什么？**
每工具和每天：运行、成功、失败、earned 总额。一张表，90 天，CSV 下载。没有调用方身份。

**10. 运行失败时制作者看到什么？**
带 `ctx.log` 行的运行日志页、失败步骤的状态和错误 body，以及调用方发的输入（带 `secret` 的输入被遮盖）。

## 积压项，按被提到的顺序

1. 更多数据提供商的模板（数据工具作为模板系统），含 `treg hub init --from <template>`（owner，2026-09-09）。
2. 把 earned credit 提现为现金。
3. 上架路径：pull request、验证、搜索里的三种目录状态。
4. hub 工具上一个 private-to-my-team 开关。
5. 卖家价格上的平台费（在开始之前宣布）。
6. 仪表盘里的脚本编辑器。
7. 运行页上对一个进行中运行的实时轮询。
8. 给脚本自己的计算计费。
9. 来自 2026-09-08 的会面：Crawl4AI 作为脚本内的内建函数；由 Tim 的 agent-feedback 工具喂的基准和审计器；一个作业队列、recipe 调 recipe、步骤重试、API 上的实时进度、以及一个团队自己的沙箱（从 `docs/RECIPES-DECISIONS.md` 继承）。
