# 目录猎手 —— 一个每周的 agent 循环，发现、分流并起草新的供应商

**状态：**已规划，待审阅。什么都没建。

## 它是什么

一个按计划运行的 agent，每周一次，让目录持续成长而无需人去打猎：

1. **收集** 来自三个来源的候选
2. **分流** 它们，对照我们已经写下的挑选规则
3. **起草** 每个存活候选的一份完整档案
4. **报告** 给 Unclecode 待批准
5. 批准后，**实现**除那一个需要人的步骤之外的所有东西

攻略已经存在：`docs/context/guides/expanding-a-category.md` 是作为可重复流程写下的，带挑选启发式和有记录的拒绝理由。这个循环就是那个指南，按日程执行，在指南本身要求有人把关的地方加一道人门。

## 三个输入

- **打猎。** 按分类做网络研究，包括新的市场数据分类（`docs/MARKET-DATA-CATEGORY-RESEARCH.md` 是可从中取用的常驻短名单）。还有：用量数据暴露的缺口 —— 一个团队反复搜却搜不到的能力，比任何榜单都更强的信号。
- **仓库上的社区 issue**，要求供应商或分类（市场数据的请求正是以这种方式进来的）。
- **供应商 PR。** 现在有七个开放外部提交（#92 risk-data、#94 Parallel、#95 Linkup、#96 LemMeBuyIt、#97 Goldsky、#119 Virlo）。这些是价值最高、今天服务最少的输入：贡献者做了起草，却没人系统地按我们的规则核对他们的工作。

## 分流：规则已经写好

来自指南，在任何一个人看到列表之前机械地应用：

- 自助 API key，无销售电话（这就是整个快速通道）
- 相对分类已有东西的清晰价值，不是一个近似重复
- 带着记录的理由拒绝：法律风险、已弃用、仅 UI、企业门槛
- 当 N 个干净的选择不存在时，如实说，而不是用差适配来填充

加上定价阶梯新加的一级：一个固定费的供应商不再被自动拒绝 —— 档案说明它定在哪个层级，对共享方案候选，说明提议的费率含费用和盈亏平衡。

## 档案（每个候选一份，批准用制品）

正是指南说重要的那些事实，允许"未确认"、禁止猜测：

    provider、分类、它填补什么缺口
    定价层级：credits / 上限 / 速率限制 / 无限 —— 带数字和来源 URL
    base_url、认证位置 + 格式
    一个廉价或免费的探测端点，以及文档记载的坏 key 行为
    ToS 红旗：再分发、非商业免费层、数据许可（市场数据尤其）
    对供应商 PR：提交的 YAML 是否匹配现实，以及 diff 审阅发现了什么
    裁决：推荐 / 拒绝（带记录理由）

## 人的接缝，直白说明

**live 的垃圾 key 测试无法被自动化掉。** 它需要真实的注册和真实的 key，而且指南明确：绝不发布一个你没看着它拒绝垃圾 key 的 key 供应商。所以循环在其自动化运行结束于"档案就绪、除 key 外已测"，批准邮件精确列出需要哪些注册。在 Unclecode（或 Jason）提供 key 之后，实现那半运行：注册表条目、logo 占位、测试、live 的垃圾 key 检查、文档。

第二道人门是批准本身：没有 Unclecode 看档案列表，什么都不添加，也不开任何 PR。循环起草；它不发货。

## 机制

- **日程：** 每周一次，作为本仓库里一个按计划运行的 agent 会话。运行的输出是一份 markdown 报告（档案 + 拒绝 + 需要的 key 列表）提交到一个分支并链接在通知里，所以审阅像其他一切一样在 VS Code 里发生。
- **状态：** 一个小的 `docs/hunter/seen.yaml`，记录已评估的候选及其裁决，所以一个被拒绝的供应商不会每周被重新辩论，而一个"还没有、价值单薄"的可以在有变化时重访。指南开启的记录-拒绝习惯变成循环的记忆。
- **供应商 PR：** 循环把它的档案发现（事实，不是决定）作为评论写在该 PR 本身上，对等待在 #92–#119 的贡献者来说这也是礼貌的。
- **成本：** 打猎是网络研究加目录读取；唯一的花费是存在免费层时的探测调用。没有批准，绝不花平台 key。

## 顺序

1. 档案格式 + `seen.yaml`，以及对七个开放 PR 的一次手动运行 END TO END —— 价值最高的那一堆，也是在存在任何日程之前证明格式的那次运行。像任何工作一样审阅。
2. 打猎那半（按分类的网络研究），第二次手动运行。
3. 只有那时才上日程，在两次手动运行证明报告值得被唤醒之后。
4. 实现那半（批准后的自动化）放最后 —— 它是指南的步骤 3–7，而且它们已经被充分指定。

刻意地：日程是第 3 步，不是第 1 步。一个无人值守的循环通过在被观察时有用两次，来挣得它的 cron 槽位。

## 可能出什么错

- **档案腐坏。** 第一周验证、第六周添加的供应商可能改了定价。档案带着它的 `checked` 日期；实现那半在写 fx 条目之前重新验证定价，而不是信任一份过时档案。
- **PR 谄媚。** 贡献者的 YAML 可能看起来完整而实际是错的（这周的 b2b-ads-search 印章来自我们**自己**验证过的工作，而且它仍然不完整）。一个 PR 的档案是从供应商文档独立构建的，然后与提交做 diff —— 绝不把提交当作来源。
- **分类填充。** 指南的规则成立：干净的挑选用完时，报告如实说。一个带配额的每周循环会为达标而编造供应商；这一个没有配额。
