# hub 上架与公开运行日志 —— 那些决策

Jason 在 2026-09-15 提的两个增补：一种把 hub 工具上架到目录的方式（至今每个 hub 工具都按决策保持未上架），以及一份该工具所服务调用的公开日志。五项决策，由 owner 在 2026-09-16 根据原型批准。

**1. 上架是工具上的一个开关，而不是 recipe.json 里的一个字段。**
默认关。制作者用 `treg hub list <id>` / `treg hub unlist <id>`、`PATCH /hub/tools/{id} {"listed": true}`，或控制台的开关来翻转它。不 bump 版本，就像改价。这是一个分发选择，不是配方契约的一部分。

**2. 一个已上架工具出现在目录搜索里；未上架的只可按 id 调用。**
在同样的结果里，按相关性排序，无加权，标为 `hub` 并带上制作者团队、价格标签和 30 天 ok 率。MCP 上的 `catalog_search` 也返回它。只有 `live` 版本会被上架；失败和已退役的永不出场。

**3. 公开日志展示结果，从不展示人或数据。**
每次运行：时间、成功或失败、时长、步骤、单位（per_unit）、支付的价格。从不展示谁调用，从不展示输入，从不展示输出。最近 20 次运行，以及 30 天内每天的运行次数。

**4. 制作者可以把公开日志关掉。**
默认开。失败的运行也展示：页面已经展示健康度，而一个藏起失败的日志不是日志。

**5. agent 页面拿到同样的日志。**
`/hub/<id>.md` 带着运行表，所以一个 agent 能在调用前判断一个工具，就像它读价格那样。

## 第二轮 —— treg 审批上架（2026-09-24，owner + Jason）

Jason 的制作者页面把搜索放在 treg 审批之后。决定：

**1. `treg hub list` 是一次请求。** 该工具只有在超级管理员从控制台 Admin 页面或 `POST /admin/hub/listings/{id}` 批准它时才进入目录搜索。拒绝会带一个制作者能读到的理由；再次上架就再次请求；unlist 会撤回请求或批准。

**2. 一次批准属于工具，而不是一个版本。** 一个新版本保持上架，管理员可以收回批准（一次带理由的拒绝）。所以状态是它自己的一行（`HubListing`），而不是每个版本上的一个列 —— 那个列会在每次发布时重置。

**3. 为什么审批。** 起初 hub 只服务少量团队；搜索里一个弱工具会让每个选它的调用方付出代价。在运行证据能胜任这项工作之前，审查让搜索值得信任。

## 第三轮 —— capability：把工具放在其工作的供应商旁边（2026-09-24，owner + Jason）

**1. 制作者命名工作；treg 批准它。** recipe.json 里的 `"capability"` 是一个目录 capability id。它是一个提案：随上架批准生效，管理员可以改或清掉它。

**2. 在旁边，绝不代替。** 一个被批准的工作把该工具放进每个提供该工作的供应商的 `catalog_get` 兄弟里，而那些供应商也出现在它自己页面的旁边。treg 不路由到它；agent 对比并挑选。

**3. 一个种子，因为新工具没有运行。** 它的成功率从 90% 开始，按 5 次运行计，其他团队的运行会移动它；大约 20 次之后种子几乎不计。在那之前数字标为 `estimated`。owner 选择在种子和隐藏新工具之间用种子：隐藏的话，一个工具永远拿不到能证明它的运行。

## 第四轮 —— 对已上架工具的每次更新都经过 treg（2026-09-24，owner + Jason）

Jason：一个制作者可能让一个工具获批，然后发布一个收费更多或返回更差数据的版本。决定：

**1. 对已上架工具的任意更新都要等审查：** 一个新版本和一次改价。被批准的版本和价格继续服务调用方、搜索以及在供应商旁边的位置，直到 treg 批准。这取代了第二轮"一次批准跨新版本保持"。

**2. 制作者仍能试它。** 一个等待中的版本只对制作者团队回答 `<id>@N`。

**3. 一次拒绝保留被批准的版本，** 把新的标为 `rejected`，丢掉新价格，并给制作者理由。

**4. 未上架工具保持自助。** 一个没人找得到的工具无需审查就发布和定价。（第五轮改变这一点，针对 treg 曾批准过的工具：unlist 后它仍处在审查下。）

## 第五轮 —— 一个作弊卖家发现了什么（2026-09-25，owner，在 hub 模拟运行 2 之后）

一个模拟卖家试了 14 种方式去改变买家得到什么或付多少。决定：

**1. 一旦批准，永远审查。** 批准、unlist、然后改价和版本曾是绕过审查的途径：保留 id 的买家为更少的东西多付了最多 50 倍。现在 unlist 一个已批准工具只是把它移出搜索；它的变更仍然等待，调用方保留被批准的版本，再次上架无需新审查。一个收回批准的拒绝也保留审查。

**2. 保留的团队名。** 一个团队 slug 是每个 hub 工具 id 的前半。读作 treg、读作官方、或读作某个目录供应商或平台的名字在创建、重命名和发布时都被拒绝，除非超级管理员出手。

**3. 一个空答案不付卖家价格**，且价格行写明 provider-fee 上限，并明白地说一次失败运行仍支付所跑步骤的费用。

**4. 公开价格一旦有任何别的团队的运行就建立在别的团队的运行上**；制作者自己的免费运行标为测试。**5. 契约写明工具把输入发往的制作者自己的服务器主机。**

未决定：当制作者自己的服务器改变时重新审查一个工具；制作者只是被披露。

## 第六轮 —— 同一个卖家再来（2026-09-25，owner，在 hub 模拟运行 3 之后）

运行 2 的洞还在。新发现的，已决定：

**1. 一个被拒绝的工具不可被其他团队调用**；它的分享页回答 410。一个从未审查的工具仍可按 id 调用，所以制作者可以在要求搜索之前构建和分享。

**2. 名字按它们被读到的样子判定：** 形近字母、数字和分隔符绕不过保留名（`trеg-hub`、`tregg`、`hunter-io`、`Hunter.io data`、`apol1o`、`verified-partner`）。

**3. 没有中继：** 一个团队工具不能指向 treg 自己。

**4. 审阅者读代码：** 脚本或步骤、一个更新 diff、以及自有工具的地址。check.json 可携带若干 case。一个制作者不能审阅自己的工具。

**5. 路由说明谁为一个 miss 计费：** 一个路由价格不再声称"你正好付给服务的那个子调用"；它点名那些为一个 miss 计费的子调用。
